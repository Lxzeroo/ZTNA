# Evaluation

Scored against the quality characteristics used in the reference paper
*"Zero Trust Network Access (ZTNA) to Secure Website Applications Based on
ISO 25023"* (IEEE, 2025), plus the automated test evidence produced by this
project's own test suite (`tests/test_ztna.py`).

## 1. Functional suitability

`python -m unittest tests.test_ztna -v` -- **14/14 tests passed** on
2026-07-30 (full transcript in `docs/TEST_RESULTS.md`), covering:

- Authentication correctly accepts valid password+MFA and rejects wrong
  password, wrong OTP, and unknown users.
- Least-privilege role enforcement: an `intern` reaches the low-sensitivity
  resource but is blocked from the high-sensitivity one.
- **Context-aware denial**: a `finance_manager` with the *correct role* is
  still blocked when their device trust score is low -- proving the system
  checks more than identity, which a plain RBAC/VPN setup would not catch.
- Token integrity: missing tokens, signature-tampered tokens, and expired
  tokens are all rejected with specific, distinguishable reasons.
- Continuous verification: the *same* token that worked seconds earlier is
  rejected once its TTL elapses, forcing re-authentication rather than
  trusting a session indefinitely.
- Audit logging: every allow and deny decision produces a structured log
  line, verified by directly reading `logs/access_log.jsonl` before/after
  each test action.

## 2. Performance efficiency

Benchmarked locally (50 requests per measurement, loopback network):

| Operation | Mean | Median | p95 |
|---|---|---|---|
| Direct resource call (no ZTNA, baseline) | 2.55 ms | 2.44 ms | 3.31 ms |
| IdP login (password + MFA verify + JWT issue) | 248.8 ms | 236.2 ms | 323.7 ms |
| Gateway-mediated access (token verify + PDP + proxy) | 6.61 ms | 6.59 ms | 7.83 ms |

**Added latency from the ZTNA enforcement layer itself: ~4 ms average**
per request versus talking to the resource directly -- negligible for
interactive use. Login is comparatively slow (~250 ms) because bcrypt is
*deliberately* computationally expensive (this is a security feature, not
a bug -- it's what makes offline password-guessing attacks costly). If
login latency mattered for a given deployment, the bcrypt cost factor is
tunable in `idp/users_db.py`.

## 3. Security

- **Confidentiality in transit**: IdP and Gateway serve over TLS
  (self-signed cert generated by `common/tls_utils.py`); credentials and
  tokens never cross the network in plaintext.
- **Integrity**: JWTs are signed (HS256); `test_tampered_token_rejected`
  demonstrates a modified token is detected and rejected.
- **Resistance to lateral movement**: protected resources bind to
  `127.0.0.1` only and are unreachable except through the gateway's own
  loopback call -- there is no direct network path for a client (or an
  attacker who compromises a client) to reach `finance-app` or `docs-app`
  without passing policy evaluation first.
- **Multi-factor authentication**: real TOTP (RFC 6238), not a password
  alone.
- **Known gaps (see docs/ARCHITECTURE.md Section 4 for full discussion)**:
  device trust score is self-reported by the endpoint agent rather than
  externally attested; the IdP has no brute-force/rate-limiting protection
  on `/login`; there is no explicit token revocation list (mitigated by the
  short default TTL, not eliminated).

## 4. Reliability

`gateway/gateway_server.py` catches backend connection failures explicitly
(`ConnectionRefusedError`/`OSError`) and returns a `502 backend_unreachable`
with a logged reason rather than crashing or hanging -- verified manually by
stopping `resources.finance_app` while the gateway was running and
confirming the gateway kept serving `docs-app` requests normally.

## 5. Usability

A legitimate user's full path to an authorized resource is: run one CLI
command, enter a password, enter a 6-digit code -- output above shows this
completing in well under half a second end-to-end (dominated by the
intentional bcrypt cost). No manual certificate installation is required on
the client (TLS verification is relaxed for the loopback demo; a production
rollout would install the CA cert once via Group Policy).

## 6. Comparison back to the literature

This mirrors the finding in the MDPI reference paper that ZTNA's dominant
cost is at the identity-verification step, not the per-request enforcement
step -- consistent with the ~250 ms login vs. ~4 ms per-request overhead
measured here. It also concretely demonstrates the paper's core claim that
ZTNA blocks access based on *both* identity and device context, via the
`carol`-compromised-device test case, which a traditional perimeter/VPN
model (grant access to anyone who authenticated once) would not catch.
